# 企画候補2：ラーニングセンター拠点・リモート配置最適化

> **学習言語・期・プロジェクトごとのグループを崩さず、ラーニングセンター、本社フロア、リモートへ条件に応じて配置する。**

## 30秒概要

ラーニングセンターでは、経験者、CL・Javaの期別グループ、FR、QA、ML、SQL PJなどの**グループ単位**で分かれており、ラーニングセンターだけでなく本社5階・8階やリモートへ配置されることがあります。基本的に1つのグループを途中で分割して別々の場所へ配置するのではなく、グループを一括りにして動かします。もし、この収容人数やグループ配置の調整が担当者の負担になっているなら、Reactで条件・配置結果を見える化し、Pythonで条件を満たす配置案を自動生成できないか、という企画です。まず担当者へヒアリングし、課題が小さければ同じ仕組みを汎用的なシフト・当番・出社日調整へ転用します。

## 1. 何を作るのか

現時点で確認できている範囲では、待機生は単純に個人単位で扱われているのではなく、次のようなグループに分かれている。

- 経験者全て
- エントリー(CL1月生)
- エントリー(CL4月生)
- エントリー(Java1月生)
- エントリー(Java4月生)
- エントリー(FR)
- エントリー(QA4月生以外)
- エントリー(QA4月生)
- エントリー(ML)
- SQL PJ

配置先もラーニングセンターだけではなく、本社5階・8階など複数あり、収容状況によってリモートになる場合もある。

重要なのは、**同じグループは基本的に一括りで、グループ内の一部だけを別拠点へ分けるような配置ではない**という点。

そのため本企画では、個々の待機生を1人ずつ最適化するのではなく、まず**「グループ」を配置の最小単位**として扱う。

```text
グループ情報
（経験者全て / CL1月生・4月生 / Java1月生・4月生 / FR / QA / ML / SQL PJ 等）
＋
グループ人数
＋
配置先
（ラーニングセンター / 本社5階 / 本社8階 / リモート等）
＋
各配置先の収容人数
＋
曜日・サポート等の条件
    ↓
Pythonでグループ単位の配置案を生成
    ↓
FastAPI
    ↓
Reactで曜日・拠点・人数・警告を表示
```

ただし、実際の定員、曜日ごとのルール、リモート頻度、サポート体制などの詳細はヒアリング前のため未確認とする。

## 2. どんな困りごとを解決するのか

### 現時点で分かっている運用

- 待機生が複数の言語・期・プロジェクトのグループに分かれている
- グループは基本的に一括りで配置される
- ラーニングセンター以外に、本社5階・8階などへ配置されることがある
- 収容人数の都合でリモートを組み合わせることがある

### まだ確認が必要なこと

担当者が実際にどのような条件を見ながら配置を決めているかは未確認。

例えば、次のような条件が存在する可能性がある。

- 各拠点・各フロアの収容人数
- グループごとの人数
- グループごとのリモート日・回数
- 学習内容に応じた配置先
- サポート担当者が対応可能な曜日・場所
- 特定グループの固定配置
- 曜日ごとの人数の偏り
- 例外的な予定・イベント

条件が少なければ表計算ソフト等でも十分対応できるが、グループと配置先、曜日、制約が増えるほど、次のような負担が発生する可能性がある。

- あるグループを移動すると各拠点の人数を再計算する必要がある
- グループを分割せずに定員内へ収める組み合わせを考える必要がある
- 日程変更のたびに他のグループ・拠点への影響を確認する必要がある
- 定員超過や割り当て漏れを目視で確認する必要がある
- 担当者しか配置ルールを把握していない状態になりやすい

本企画では、**担当者の判断をなくすのではなく、条件をシステムへ入力して配置候補を自動生成し、最終判断を担当者が行えるようにする**ことを価値とする。

### 最初に確認すべきこと

企画採用前後に、実際の調整担当者へヒアリングする。

1. 現在は何を使って配置を調整しているか
2. グループはどのような単位で管理しているか
3. グループを分割する例外はあるか
4. 配置先にはどこがあり、それぞれ何人まで入れるか
5. リモート日はどのようなルールで決めているか
6. 絶対に守る条件は何か
7. できれば守りたい条件は何か
8. 急な変更が起きたとき、どこが大変か
9. 自動生成されるなら、どこまで自動化してほしいか
10. このようなツールが実際にあれば使いたいか

「困っていない」「既存手段で十分」という結果も、有効な企画検証結果として扱う。

## 3. どう解決するのか

条件を、まず2種類に分けて扱う。

### 絶対に守る条件（Hard Constraints）の例

- 各拠点・フロアの最大収容人数を超えない
- 1つのグループを途中で分割しない
- 1グループは、その日の配置先を1つにする
- 固定配置がある場合はその条件を守る

### できれば満たしたい条件（Soft Constraints）の例

- 拠点ごとの人数をなるべく偏らせない
- リモート日が特定のグループに偏らない
- 必要なサポートを受けやすい配置を優先する

Python側で条件を評価し、グループ単位で配置可能な案を生成する。

React側では、生成結果だけでなく、

- 曜日ごとの配置
- 拠点・フロアごとの総人数
- 配置されているグループ
- 定員までの残り人数
- リモート対象グループ
- 条件違反
- 手動変更後の再チェック

などを確認できるようにする。

> [!NOTE]
> Hard / Soft Constraintの具体的な内容は仮案。実際の運用ルールをヒアリングした後に確定する。

## 4. 想定する主な機能

### 機能A：グループ・配置先・基本条件の入力

- グループ一覧を登録・表示する
- グループ名、カテゴリ、人数を設定する
- ラーニングセンター、本社フロア等の配置先を登録する
- 配置先ごとの定員を設定する
- 曜日別・固定配置等の条件を必要に応じて設定する

### 機能B：配置案の自動生成

- 条件をFastAPIへ送信する
- Pythonでグループを分割せず配置先へ割り当てる
- 各配置先の定員を超えないよう判定する
- 条件を満たせない場合は理由を返す
- 生成結果をReactへ返す

### 機能C：結果確認・調整

- 曜日・拠点別の人数を表示する
- どのグループがどこに配置されたか確認する
- 定員超過や条件違反を警告する
- 将来的にはグループを手動で別拠点へ移動し、再検証する

- Pythonの基本

- Pydantic等による入力検証

- グループ単位のデータモデル

最初から高度な最適化ライブラリへ依存せず、Phase 1では単純なルールベース・探索から始めることもできる。

## 7. 3人でどう縦割りできそうか

| 担当機能の例 | React側 | Python側 |
| --- | --- | --- |
| グループ・拠点条件 | グループ・人数・定員入力 | 入力検証、制約モデル化 |
| 配置案生成 | 配置実行、結果表示 | グループ単位の割り当て・探索 |
| 結果検証・調整 | 拠点別人数、警告、手動変更 | 条件違反検出、再評価、スコアリング |

各自が、**Reactで条件を入力 → FastAPIへ送信 → Pythonで判定・計算 → 結果をReactへ表示**という縦の流れを経験できる構成を目指す。

具体的な分割は、ヒアリングで判明した実際の条件とPhase 1の範囲に合わせて再調整する。

## 8. 14営業日の最小構成

### Phase 1：グループを崩さず、定員内へ配置する

実際の個人情報は使わず、まずダミーのグループデータを用いる。

例：

```text
グループ：10グループ
- 経験者全て
- エントリー(CL1月生)
- エントリー(CL4月生)
- エントリー(Java1月生)
- エントリー(Java4月生)
- エントリー(FR)
- エントリー(QA4月生以外)
- エントリー(QA4月生)
- エントリー(ML)
- SQL PJ

各グループ：それぞれ人数を持つ
配置先：ラーニングセンター / 本社5階 / 本社8階 / リモート
各物理拠点：定員を持つ
ルール：グループは分割しない
```

この条件から、グループを一括りのまま、各物理拠点が定員以内になる配置案を生成する。

```text
ダミーグループデータ
＋
各配置先の定員
＋
グループ分割禁止
    ↓
ReactからFastAPIへ送信
    ↓
Pythonで配置案生成
    ↓
結果JSON
    ↓
Reactで拠点別・グループ別に表示
```

### Phase 1の完成条件（仮）

- Reactからグループ、人数、配置先、定員を入力・送信できる
- Python側でグループ単位の配置案を実際に生成できる
- グループが複数の配置先へ分割されていない
- 各物理拠点の合計人数が定員以内になっている
- 条件を満たせない入力では、適切に失敗理由を返せる
- React上で各拠点の人数と配置グループを確認できる
- ReactとPythonをモック同士で終わらせず、実APIを通した結合確認ができる
- 正常系・定員不足・グループ人数境界値など、代表的なケースを自動テストできる

> [!IMPORTANT]
> 実際の現場条件はヒアリング前のため、これは企画比較用の仮完成条件。企画採用後、必要性が確認できた場合に実際の運用条件へ置き換える。

## 9. テストしやすさ

スケジューリングは入力条件と満たすべき制約を固定できるため、Phase 1は比較的テストしやすい。

例えば、

- グループ人数の合計が各拠点の定員内 → 配置可能
- 1グループが2つの拠点へ分割されていないことを確認
- ある拠点へ配置すると定員超過 → 別拠点またはリモートへ配置
- どの組み合わせでも条件を満たせない → 配置不能として返す
- 定員とグループ人数が同じ → 境界値として配置可能

など、入力と満たすべき条件を明示できる。

将来的に最適化を高度化した場合も、特定の「唯一の正解配置」をテストするのではなく、**生成結果がすべてのHard Constraintを満たしているか、評価値が期待範囲か**をテストする。

## 10. その後どう拡張できるか

### Phase 2：実際の運用条件を追加

ヒアリングで必要性が確認できた条件だけを追加する。

例：

- 曜日ごとの配置
- グループごとのリモート頻度
- 固定配置されるグループ
- 学習内容と配置先の関係
- サポート担当者の対応可能日・場所
- 一時的な利用不可フロア

### Phase 3：複数案・評価

複数の配置候補を生成し、

- 各拠点の定員利用率
- 人数の偏り
- リモート配置の偏り
- サポート条件の満たしやすさ

などで比較できるようにする。

### Phase 4：手動変更と再最適化

担当者がグループ単位で配置先を手動変更したあと、条件違反を検出したり、残りのグループだけを再計算できるようにする。

### 代替案：汎用シフト・スケジュール調整

ラーニングセンター側で課題が確認できなかった場合は、技術構成を活かして、

- 店舗シフト
- 当番表
- 出社日調整
- 会議室・設備割り当て
- 研修日程

などの汎用的な制約付きスケジューリングへ対象を変更できる。

## 11. ポートフォリオとして何をアピールできるか

- 実際の利用者候補へのヒアリングから課題を検証する開発プロセス
- 課題仮説を事実として決めつけず、検証して要件へ落とす経験
- React / TypeScriptとPython / FastAPIを組み合わせたフルスタック開発
- 実際の業務構造に合わせて「個人」ではなく「グループ」を配置単位としてモデル化した設計
- Hard Constraint / Soft Constraintを意識した要件整理
- 制約付きスケジューリング・組み合わせ探索
- 条件を満たさないケースも含めたAPI・エラー設計
- 3人がReact → Pythonまで機能単位で縦割りする共同開発
- 自動生成結果を人間が確認・修正するHuman-in-the-loop型の設計
- フェーズごとに完成条件を設定し、小さく改善する開発

特に、実際の担当者にヒアリングして課題が確認できれば、**「身近な現場の複雑な配置問題を整理し、実際の運用単位に合わせて技術で支援した」**という説明ができる。

## 12. 技術的な懸念・事前調査が必要なこと

- そもそも現在の調整作業が負担になっているか
- 現在どのツール・手順で調整しているか
- グループは常に一括配置なのか、例外的に分割するケースがあるか
- ラーニングセンター、本社5階・8階以外にも配置先があるか
- 各配置先の実際の定員はどのように管理しているか
- リモート日はグループ単位でどのように決めているか
- 実際に考慮している制約条件は何か
- 自動化してよい判断と、人が決めるべき判断の境界
- 解が複数存在するとき、何を「良い配置」と評価するか
- 解が存在しない場合のユーザーへの説明方法
- Phase 1を単純なルールベースで実装するか、最適化ライブラリを使うか
- OR-Tools等を使う場合の学習コストと必要性
- 実データを扱う場合の個人情報・アクセス権・データ管理
- 3人へ十分なReact / Python実装を分配できる機能粒度

企画段階では、未確認事項を無理に確定せず、採用候補になった段階でヒアリングと技術調査を行う。

## 13. 技術構成（候補）

| 領域 | 技術 | 役割 / 採用理由 |
| --- | --- | --- |
| Frontend | TypeScript + React | グループ・拠点条件入力、カレンダー、拠点別人数可視化、警告、手動調整 |
| API | Python + FastAPI | 条件受付、配置処理呼び出し、結果・失敗理由返却 |
| Scheduling | まずPython標準機能で検討 | Phase 1のグループ単位の割り当て・制約判定 |
| Optimization | OR-Tools等を必要に応じて検討 | 制約や目的関数が複雑になった段階で採用判断 |
| Database | PostgreSQLを後続Phaseで検討 | グループ、配置先、条件、スケジュール、履歴等の保存 |

重要なのは最適化ライブラリを使うこと自体ではなく、**実際の課題に対して、何を1つの配置単位とし、どの条件を守り、何を最適化したいのか説明できること**とする。

## 14. 今回やらないこと

Phase 1では、以下を最初から対象にしない。

- 実際の待機生の個人情報を使った運用
- 全ての現場ルールの再現
- 完全自動での配置確定
- 高度なAIによる判断
- 複雑な権限管理
- 外部勤怠システムとの連携
- 完璧な最適解の保証

まずはダミーデータで、**グループ・条件入力 → Pythonで配置 → Reactで確認**という最小の価値を完成させる。
