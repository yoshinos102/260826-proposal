# 1. 30秒で分かる概要

## 何を作るのか

SES企業における、**「案件提案 → 顔合わせ対策 → 顔合わせ結果の記録 → 次回への改善」**までを支援する社内向けWebアプリを作る。

営業担当者が案件情報を登録し、社員のスキルシートと組み合わせることで、その案件で聞かれそうな質問や、本人が強調すべき経験、説明不足になりそうなポイントなどを整理・生成する。

さらに、実際の顔合わせで聞かれた質問、結果、フィードバック、見送り理由などを保存し、会社の顔合わせノウハウとして蓄積・再利用できるようにする。

## 誰のどんな困りごとを解決するのか

主な利用者は、SES企業の営業担当者・社員・管理者を想定する。

現在の顔合わせ対策には、以下のような問題がある。

- 案件ごとに何を質問されるのか予測しづらい
- 社員本人が、自分のどの経験をアピールすべきか分かりづらい
- 「基本設計を経験した」「AWSを使った」など説明が抽象的になりやすい
- 対策の質が、営業担当者や社員本人の経験に依存する
- 過去の質問や見送り理由が個人の記憶に残り、会社のノウハウとして蓄積されにくい

## 一言でいうとどんなアプリか

> **案件と社員の情報から顔合わせ対策を作り、実際の結果を会社のナレッジとして蓄積・再利用するSES企業向け顔合わせ支援システム。**

単なる「AI面接練習アプリ」ではなく、**SES企業の顔合わせ業務そのものを改善する社内業務システム**を目指す。

# 3. 何を作るのか

SES企業における顔合わせ準備と結果管理を一元化するWebアプリを作る。

基本的な流れは以下とする。

```text
案件登録
↓
社員登録・スキルシート登録
↓
案件に社員をアサイン
↓
案件情報 × 社員情報を分析
↓
顔合わせ対策を生成
↓
必要に応じて模擬顔合わせ
↓
本番の顔合わせ
↓
結果・質問・フィードバックを登録
↓
データを蓄積
↓
次回の顔合わせ対策に活用
```

営業担当者は案件情報を登録し、顔合わせを受ける社員を選択する。

システムは案件の必須スキル・担当工程・業務内容などと、社員の技術経験・担当工程・過去プロジェクトなどを比較し、

- 聞かれそうな質問
- 強調した方がよい経験
- 深掘りされそうな経歴
- 説明不足になりそうなポイント

などを提示する。

顔合わせ終了後には、

- 実際に質問された内容
- 結果
- 社員の回答
- 営業・顧客からのフィードバック
- 見送り理由

などを登録する。

これらを蓄積することで、個人の経験に依存していた顔合わせ対策を、会社全体のナレッジとして再利用できる状態を目指す。

# 4. どんな困りごとを解決するのか

## 4.1 案件ごとに質問を想定しづらい

同じJava案件でも、

- Spring Boot経験
- 基本設計経験
- AWS経験
- 顧客折衝経験

など、案件によって確認されるポイントが異なる。

案件票を読んだだけでは、「実際に何を聞かれそうなのか」を社員本人が判断するのは難しい。

## 4.2 どの経験をアピールすればよいか分からない

社員に複数のプロジェクト経験があっても、今回の案件に対してどの経験が重要なのか判断しづらい。

例えばSpring Boot案件であれば、

- REST APIを実装した経験
- ControllerからRepositoryまで担当した経験
- JUnitを利用した経験

など、案件との関連性が高い経験を優先して説明する必要がある。

## 4.3 経験の説明が抽象的になりやすい

例えば、

```text
基本設計を担当しました。
AWSを使いました。
APIを作りました。
```

だけでは、実際に何を担当したのか伝わりにくい。

「何を作ったか」「どこまで自分が担当したか」「どのような工夫をしたか」まで整理する必要がある。

## 4.4 対策方法が属人化している

営業担当者によって、

- どこまで対策するか
- どんな質問を想定するか
- どの経験を深掘りするか

が変わりやすい。

社員本人の面談経験によっても対策の質に差が出る。

## 4.5 過去の結果が会社の資産になりにくい

実際に聞かれた質問や見送り理由が営業担当者や社員本人の記憶だけに残り、次の社員に共有されないことがある。

同じような案件で過去に何度も聞かれている質問があっても、新しい社員がゼロから対策することになってしまう。

# 5. どう解決するのか

案件情報・社員情報・顔合わせ結果を一つのシステムで管理する。

## 案件 × 社員から対策を作る

例えば案件に、

```text
必須スキル
- Java
- Spring Boot

担当工程
- 基本設計
- 製造

インフラ
- AWS

その他
- 顧客折衝あり
```

と登録され、社員に、

```text
Java：4年
Spring Boot：2年
AWS：EC2 / S3経験
基本設計：1年
```

と登録されている場合、以下のような対策を提示する。

### 想定質問

1. Spring Bootではどのような機能を実装しましたか？
2. 基本設計では具体的に何を担当しましたか？
3. AWSではどのサービスを利用しましたか？
4. 障害対応の経験はありますか？
5. 顧客と直接やり取りした経験はありますか？

### 重点的に伝える経験

- Spring Bootを使用したREST APIの実装経験
- 基本設計から結合テストまで担当した経験
- AWS EC2 / S3を利用した経験

### 注意ポイント

- AWS経験が浅い場合は、実際に担当した範囲を明確に説明する
- 「基本設計を担当した」だけでなく、作成した成果物まで説明する
- 顧客折衝経験は、誰と・何を・どのように調整したのか具体化する

## 結果を保存して次回へつなげる

顔合わせ後に実際の質問や結果を保存する。

データが蓄積すれば、将来的には、

```text
Spring Boot案件 × 経験2〜3年

過去の顔合わせでは、

・担当工程
・API設計経験
・JUnit
・SQL

について質問される割合が高い
```

といった、過去実績をもとにした対策も可能になる。

つまり、

```text
対策する
↓
顔合わせを受ける
↓
結果を記録する
↓
会社のナレッジが増える
↓
次の対策の精度を高める
```

というサイクルを作る。

### 例

- 基本設計では具体的にどのような作業をしましたか？

#### Java

- Javaではどのような処理を実装しましたか？

- AWSではどのサービスを利用しましたか？

---

## 6.6 STAR形式による回答整理

社員の経験を面談で説明しやすくするため、STAR形式で整理できるようにする。

| 項目 | 内容 |
|---|---|
| Situation | どのようなシステム・状況だったか |
| Task | 自分の担当や課題は何だったか |
| Action | 自分が具体的に何をしたか |
| Result | その結果どうなったか |

「経験したことはあるが、説明がうまくできない」という状態を減らす。

## 担当間の依存を減らす工夫

14営業日という短期間では、担当間の待ち時間を減らすことが重要になる。

そのため、

- API仕様を最初に決める
- DBの主要テーブルを最初に決める
- 各担当が自分の機能をフロントからDBまで完結させる
- 他担当のAPIが未完成でもモックデータで画面開発できるようにする

といった進め方が適している。

---

# 10. 14営業日の最小構成

14営業日で全機能を完成させるのではなく、

> **「案件と社員を登録し、その組み合わせから顔合わせ対策を作り、結果を残せる」**

ところまでを完成条件とする。

## MVPの完成条件

1. 案件を登録できる
2. 案件一覧・詳細を確認できる
3. 社員とスキル情報を登録できる
4. 社員一覧・詳細を確認できる
5. 案件と社員を選択できる
6. 案件情報と社員情報から想定質問を生成できる
7. アピールポイントまたは注意ポイントを表示できる
8. 顔合わせ結果を登録できる
9. 過去の顔合わせ結果を一覧で確認できる

## MVPの基本フロー

```text
案件登録
↓
社員登録
↓
案件 × 社員を選択
↓
想定質問・アピールポイントを生成
↓
顔合わせ結果を保存
↓
履歴として確認
```

## 14営業日では原則入れない機能

完成度を優先するため、以下はフェーズ2以降とする。

- 本格的なAI模擬顔合わせ
- 音声入力
- AIによる回答採点
- STAR回答支援
- 高度なダッシュボード
- 過去データを利用した高度な推薦
- 待機社員自動マッチング
- 詳細な権限管理
- 全文検索
- 非同期AI処理
- 監査ログ

特にAI機能については、MVPでは**「案件 × 社員から想定質問を生成する」1機能に絞る**ことで開発リスクを下げる。

## 11.2 STAR形式での回答整理

社員が回答を、

- Situation

- Result

に分けて整理できるようにする。

---

## 11.3 AI模擬顔合わせ

AIを面談担当者役にして対話形式で練習する。

例：

> 今回はSpring Bootの案件ですが、これまでどのようなAPIを実装されましたか？

社員が回答すると、

> 具体的にはどのようなAPIでしょうか？  
> また、ご自身の担当範囲も教えてください。

のように追加で深掘りする。

---

## 11.4 AIによる回答評価

模擬顔合わせ終了後に、

| 評価項目 | スコア例 |
|---|---:|
| 技術説明 | 72 |
| 具体性 | 54 |
| 簡潔さ | 81 |
| 案件との関連性 | 68 |

のような評価を行う。

さらに、

> 「APIを作った」だけでは具体性が不足している

といったフィードバックを提示する。

改善例：

> Spring Bootを使用して、注文登録・検索APIを実装しました。ControllerからRepositoryまで担当し、入力チェックと例外処理も実装しました。

# 12. 技術的な懸念点・調査事項

この項目は元企画では詳細が定義されていないため、実装前に確認しておいた方がよい内容を補足する。

## 12.1 AIをどこまでMVPに含めるか

最大の懸念点。

AIを利用すると、

- API仕様の理解
- プロンプト設計
- 出力形式の安定化
- APIエラー処理
- 利用料金
- レスポンス時間

など、通常のCRUD以外の課題が増える。

14営業日では、

> 案件情報 × 社員情報 → 想定質問・アピールポイント生成

だけに絞るのが現実的。

---

## 12.2 AI出力をどの形式で受け取るか

文章だけで返させるとReact側で扱いづらいため、

```json
{
  "questions": [],
  "appeal_points": [],
  "warnings": []
}
```

のような構造化データとして取得できるか調査する。

また、不正な形式が返った場合のエラー処理も必要になる。

---

## 12.3 対策生成をAIだけに依存させるか

すべてAI任せにすると、

- 同じ条件でも結果が変わる
- 不正確な回答が生成される可能性がある
- 動作確認やテストが難しくなる

という問題がある。

そのため、

```text
DB上の案件・社員情報をPythonで比較
↓
一致 / 不足スキルなどを抽出
↓
その結果をAIへ渡す
↓
自然な想定質問へ変換
```

のように、**通常のロジックとAIを組み合わせる構成**も検討する。

---

## 12.4 DB設計

社員のスキルシートは構造が複雑になりやすい。

例えば、

```text
社員
 ├ スキル
 └ プロジェクト
      ├ 使用技術
      └ 担当工程
```

という関係になる。

案件側にも複数の必須スキルがあるため、多対多のテーブル設計が必要になる可能性がある。

開発開始前にER図を作成した方がよい。

---

## 12.5 顔合わせデータの設計

「1回の顔合わせに複数の質問がある」ため、

```text
顔合わせ
↓
質問1
質問2
質問3
```

という1対多の関係を適切に設計する必要がある。

フィードバックや見送り理由についても、

- 自由記述
- マスタから選択

のどちらにするか検討する。

---

## 12.6 検索方式

将来的に、

- Java
- Spring Boot
- AWS
- 基本設計

などで過去データを横断検索する場合、どの情報を構造化して保存するかが重要になる。

MVPの段階から技術名などを単なる自由入力だけにすると、後から集計しづらくなる可能性がある。

---

## 12.7 認証・権限制御

将来的には、

- 管理者
- 営業
- 社員

で閲覧・編集できる範囲が異なる可能性がある。

ただし14営業日では実装量が増えるため、MVPでどこまで対応するか事前に決める必要がある。

---

## 12.8 個人情報・社内情報の取り扱い

社員の経歴や顧客案件情報を扱うため、実際の業務利用を想定する場合は、

- AI APIへ送ってよい情報
- 個人情報
- 顧客名
- 機密情報
- データ保存方針

などを確認する必要がある。

ポートフォリオでは実在の案件・社員情報ではなく、ダミーデータを利用する方が安全。

---

## 12.9 14営業日での開発量

特に注意したいのは、

- AI模擬面談
- 回答採点
- 高度な分析
- 認証
- 全文検索

などを同時に実装しようとすると、完成しない可能性が高くなること。

最初はCRUDと基本フローの完成を優先する。

## 13.2 Python

Python側では、

- CRUD
- DBアクセス
- データ比較
- データ集計
- AI API連携

など幅広い処理を実装できる。

```text
React
↓ REST API

↓
Database
```

という一般的なWebアプリケーション構成を経験できる。

## 13.5 Gitを使った3人でのチーム開発

3人で機能を縦割りすることで、

- ブランチ運用

- コンフリクト対応

---

## 13.6 独自ロジック

単純に登録した内容を表示するだけではなく、

```text
案件情報
＋
社員のスキル
↓
一致する経験を抽出
↓
不足している経験を判定
↓
想定質問・アピールポイントを作成
```

という独自の処理を作れる。

AIを利用する場合でも、すべてをAIへ丸投げせず、Python側で比較・判定したデータをAIへ渡す構成にすれば、より技術的な説明がしやすい。

---

## 13.7 AIを業務フローの中で利用している点

単なるAIチャットではなく、

```text
案件登録
↓
社員アサイン
↓
対策生成
↓
顔合わせ
↓
結果蓄積
↓
分析
```

という業務フローの中の一機能としてAIを利用する。

そのため、単純なChatGPTラッパーとの差別化ができる。

---

## 13.8 「蓄積して改善する」という企画設計

この企画の特徴は、対策生成だけで終わらない点にある。

```text
対策生成
↓
実際の顔合わせ
↓
結果登録
↓
ナレッジ蓄積
↓
次回の対策へ利用
```

というフィードバックループを持つ。

ポートフォリオ説明では、

> 「AIで質問を生成するアプリを作りました」

だけではなく、

> 「属人化しているSES企業の顔合わせ対策を標準化し、実施結果を会社のナレッジとして蓄積・再利用する業務システムを設計しました」

と説明できる。

---

# 企画の中心となる考え方

この企画で最も重要なのは、

> **案件ごとに顔合わせ対策を作るだけでなく、実際の結果を会社のナレッジとして蓄積し、次の顔合わせに活かすこと。**

単なる「AI面接練習アプリ」ではなく、

> **SES企業の顔合わせプロセスを改善する社内業務システム**

として設計することで、実用性とポートフォリオとしての説明力の両方を持たせる。
